## Executive Decision

Build the first version as a mobile-first PWA with a small backend for AI calls.

Reason: the product will be used with a phone in a storage room. A PWA gives camera,
QR scanning, offline-ish local storage, and fast iteration without App Store work.
The backend exists only because AI provider keys must not be shipped to the browser.

Recommended stack:

- Frontend: TypeScript, React, Vite.
- Local data: IndexedDB through Dexie.
- Backend: small Node/TypeScript API only when cloud AI or remote local inference is
  needed.
- Item extraction: provider adapter behind one `extractItemsFromPhotos` interface.
  The adapter must support both cloud AI and local open-weight models.
- QR: generated from stable local box IDs and scanned in the PWA.
- Tests: Vitest for units, Playwright for user flows, small eval fixture for AI output.

## Step 0: Scope Challenge

### What already exists

- Product design exists in `docs/ai-box-catalog-design.md`.
- There is no implementation code yet.
- There is no app scaffold, no data model, no test framework, and no existing UX.

### Minimum complete version

The smallest complete build is:

1. Create/select a box.
2. Assign a human-readable box number.
3. Generate a QR code for the box.
4. Add/delete items manually.
5. Add photos to a box.
6. Send photos to AI for item suggestions.
7. Let the user add all suggestions or selected suggestions.
8. Search confirmed items by natural language.
9. Show matching box and photo evidence.

Anything beyond that is deferred.

### Complexity check

The plan should stay under these initial modules:

- `app/` or `src/` for frontend screens and domain code.
- `server/` for AI proxy endpoints.
- `tests/` for unit and e2e tests.

If implementation introduces more than two domain services before the first working
flow, it is overbuilt. Keep services to:

- `BoxRepository`
- `AiItemExtractionService`
- `SearchService`

### Search check

Use platform primitives where possible:

- Use browser camera input instead of custom native camera code.
- Use IndexedDB instead of building a custom local persistence layer.
- Use provider structured outputs or strict JSON-schema validation for item
  extraction instead of parsing prose.
- Use embeddings or normalized keyword matching for search, but start with a hybrid
  approach that works on tiny local datasets.

If OpenAI is chosen later, verify the exact current API shape against official docs
before implementation:

- Vision/image input support.
- Structured output support.
- Embedding support, if keyword and attribute search are not enough.

### Distribution check

For MVP, distribution is local development plus a hosted preview URL.

Do not build App Store packaging, paid downloads, subscriptions, or physical label
fulfillment until the storage-room workflow works.

## NOT in Scope

- Native iOS/Android app: too much setup before proving the flow.
- User accounts: not needed for personal MVP.
- Sharing: useful later, not needed to find the user's own things.
- Payment: premature.
- Subscription or pay-per-search: product value not proven yet.
- Exact object highlighting on photos: high-risk computer vision work, v2 only.
- Insurance inventory, warranty documents, serial numbers: turns the product into
  Itemtopia, not the focused box finder.
- Cloud photo library: start local-first and only send images for AI extraction.
- Multi-home or multi-location model: defer until one storage room works.

## Domain Model

### Box

Fields:

- `id`: stable UUID.
- `number`: human-readable number, unique per local catalog.
- `label`: optional user label.
- `qrPayload`: deep link or local route containing `boxId`.
- `createdAt`.
- `updatedAt`.

Rules:

- Box number must be unique.
- Box deletion should be blocked or require confirmation if it contains items/photos.
- QR must resolve to a box even if the box number later changes.

### Item

Fields:

- `id`: stable UUID.
- `boxId`.
- `name`: canonical confirmed name, for example `black gloves`.
- `aliases`: optional search aliases.
- `attributes`: color, category, season, material if known.
- `source`: `manual` or `ai_confirmed`.
- `sourcePhotoIds`: photo IDs that supported the item suggestion.
- `createdAt`.
- `updatedAt`.

Rules:

- Search only uses confirmed items.
- AI suggestions are not items until accepted.
- Duplicate names in one box should merge or warn, not silently create clutter.

### BoxPhoto

Fields:

- `id`: stable UUID.
- `boxId`.
- `localBlobKey`: local photo/blob reference.
- `thumbnailBlobKey`.
- `takenAt`.
- `positionHint`: optional, for example `top`, `left side`, `angle 2`.

Rules:

- One box can have many photos.
- Each photo belongs to exactly one box.
- Item extraction can run over one photo or multiple photos from the same box.
- Suggestions should keep `sourcePhotoIds` so search results can show the photos
  that justify a match.
- Keep thumbnails for search results.
- Original photos can be retained locally for MVP, but the app needs a setting later
  for storage cleanup.

### ExtractionJob

Fields:

- `id`.
- `boxId`.
- `photoIds`.
- `status`: `pending`, `running`, `needs_review`, `failed`, `applied`.
- `suggestions`.
- `errorMessage`.
- `createdAt`.
- `updatedAt`.

Rules:

- Jobs must be retryable.
- A job can reference multiple photos from the same box.
- A job must not mix photos from different boxes.
- Applying a job is idempotent: accepting the same suggestion twice must not create
  duplicate items.

### ItemSuggestion

Fields:

- `id`.
- `name`.
- `attributes`.
- `confidence`: optional model confidence or app-derived score.
- `sourcePhotoIds`.
- `reason`: short explanation, for example `visible black gloves in photo 2`.
- `selectedByDefault`: boolean.

Rules:

- Suggestions are disposable.
- User can select all, select some, rename, delete, or add missing items.

## Item Recognition Plan

The product needs "item list from messy box photos", not classic object detection
alone.

Model options:

1. Local VLM, recommended first experiment.
   - Examples: Qwen2.5-VL, LLaVA through Ollama, Florence-2 style vision foundation
     models.
   - Strength: can answer "list visible items in this box photo" and return names.
   - Weakness: may hallucinate, miss hidden objects, and needs local CPU/GPU time.

2. On-device phone inference, possible but not the first recommended MVP path.
   - Examples: MobileVLM-style models through llama.cpp, SmolVLM-class 500M models
     through ONNX/native runtimes, MediaPipe/LiteRT tasks on Android/iOS.
   - Strength: no token cost, better privacy, works without network after install.
   - Weakness: model packaging, memory, battery, device fragmentation, and weaker
     quality on messy box photos.

3. Open-vocabulary detector, useful later.
   - Examples: YOLO-World, Grounding DINO.
   - Strength: can detect prompted classes such as `gloves`, `dress`, `cable`.
   - Weakness: usually needs a vocabulary prompt; it is worse at "discover everything
     in this messy box" without guidance.

4. Cloud VLM, optional quality baseline.
   - Strength: likely best quality and simplest API.
   - Weakness: token/image cost and privacy concerns.

Recommendation:

Start with local VLM mode plus manual confirmation. If the product must run fully
on the phone, treat that as a native-app experiment after the capture/search UX is
proven. Keep cloud VLM as a behind-the-same-interface fallback for benchmarking only,
not as an MVP dependency.

The extraction output must always be treated as suggestions. User confirmation is
still mandatory.

## API Plan

### `POST /api/extract-items`

Request:

- `boxId`
- `photos`: compressed images or uploaded file IDs, depending on implementation.
- `mode`: `local-vlm` or `cloud-vlm`.

Response:

```json
{
  "suggestions": [
    {
      "name": "black gloves",
      "attributes": {
        "color": "black",
        "category": "clothing"
      },
      "sourcePhotoIndexes": [1],
      "reason": "dark gloves visible near the top-left of photo 2"
    }
  ]
}
```

Implementation notes:

- Use a strict schema for model output.
- Reject oversized photos.
- Strip image metadata before sending to AI when possible.
- Return partial results if one photo is unclear but the call succeeds.
- Never persist unconfirmed AI suggestions as final items.
- Log which extraction mode produced the suggestions so quality can be compared later.

## Search Plan

Start with hybrid local search:

1. Normalize text:
   - lower-case
   - trim punctuation
   - normalize simple color/category words
2. Score item fields:
   - exact phrase match
   - token overlap
   - alias match
   - attribute match
3. Group results by box.
4. Attach photo evidence from `sourcePhotoIds`.

Add embeddings only when keyword/attribute matching fails on real test data.

Why: the first dataset is tiny. A 10-box personal storage room does not need a full
vector database on day one.

## UX States

### Box List

- Empty: prompt to create first box.
- Normal: list boxes by number, search entry visible.
- QR scan: route directly to box card.

### Box Card

- Shows box number, QR, item count, photos, item list.
- Actions: add item manually, add from photo, delete item.

### Photo Review

- Loading: extraction is running.
- Success: list suggestions with checkboxes.
- Add all: accepts all selected suggestions.
- Add selected: accepts only checked suggestions.
- Edit: rename suggestion before accepting.
- Failed: retry, or add manually.

### Search Results

- Empty query: recent boxes or prompt.
- No results: offer to search photos later, but for MVP show "No confirmed item found."
- Results: box number, matched item, matched terms, photo thumbnail.
- Ambiguous: show multiple candidates, do not overclaim certainty.

## Edge Cases

- User scans QR for deleted box: show recoverable "box not found" with option to pick
  another box.
- User scans old QR after box number changed: route by stable `boxId`, not number.
- Duplicate box number: block save.
- Duplicate item suggestion: merge or warn.
- AI returns nonsense: keep suggestions review-only and require confirmation.
- AI times out: keep photos and failed job, allow retry.
- User goes offline during extraction: keep photos locally, retry later.
- User closes app during extraction: job remains pending/running and can recover.
- User adds item manually while extraction is running: applying suggestions must not
  overwrite manual edits.
- Very long item name: UI truncates visually but stores full name.
- 100+ items in one box: item list remains searchable and does not become unusable.
- Photo storage grows too large: not solved in MVP, but must be visible as future work.

## Failure Modes

| Codepath | Failure | Handling | Test |
|---|---|---|---|
| Create box | duplicate number | validation error | unit + UI |
| Scan QR | box missing | clear not-found state | e2e |
| Add manual item | empty name | block save | unit + UI |
| Delete item | accidental tap | confirmation or undo | e2e |
| Capture photo | browser camera denied | show file-upload fallback | e2e |
| Extract items | provider timeout | failed job + retry | unit + e2e |
| Extract items | invalid AI JSON | reject response + retry/manual fallback | unit |
| Apply suggestions | duplicate acceptance | idempotent apply | unit |
| Search | no matches | clear empty state | unit + e2e |
| Search | many weak matches | ranked candidates, no fake certainty | unit |

Critical gaps to avoid:

- Silent AI failure.
- Persisting unreviewed suggestions as real items.
- Losing photos after a failed extraction.
- QR tied to mutable box number instead of stable box ID.

### AI Eval Fixture

Before integrating a live model, create a small fixture set:

- 3 real boxes.
- 2-3 photos per box.
- Expected item list per box.
- 5 search queries per box.

Eval success:

- Extraction suggests at least 70% of obvious visible items.
- Search returns the correct box in top 2 for each known query.
- False positives are acceptable only if the result includes photo evidence and does
  not hide the correct answer.

## Performance Plan

MVP target:

- Box list opens under 500 ms with 50 boxes.
- Search returns under 200 ms for 1,000 confirmed items.
- Photo extraction can be slow, but must show progress and retry.
- Photos are compressed before local storage and before AI upload.

Avoid:

- Re-embedding or re-extracting every item on every search.
- Storing full-resolution originals without a storage story.
- Sending the same photo to AI multiple times after a retry unless explicitly needed.

## Security and Privacy

- Do not put AI provider keys in frontend code.
- Backend endpoint must validate file size and content type.
- Strip EXIF metadata before upload where possible.
- Store photos locally for MVP unless the user explicitly sends them for extraction.
- Do not log image payloads.
- Do not log item names in production analytics without explicit opt-in.

## Parallelization Strategy

Sequential implementation is recommended until Phase 1 data model is stable.

After Phase 1, work can split:

| Step | Modules touched | Depends on |
|---|---|---|
| QR | frontend routes, QR utilities | Phase 1 |
| Photo capture | frontend capture, storage | Phase 1 |
| AI backend | backend API, AI adapter | Phase 1 |
| Search results UX | frontend search, SearchService | Phase 1 |

Parallel lanes:

- Lane A: QR.
- Lane B: Photo capture.
- Lane C: AI backend.
- Lane D: Search result UX.

Execution order:

1. Build Phase 1 sequentially.
2. Build lanes A, B, C, D in parallel if using multiple worktrees.
3. Merge.
4. Integrate photo extraction review flow.
5. Run E2E and eval fixtures.

Conflict flags:

- Photo capture and AI review both touch box card UI. Coordinate or keep sequential.
- SearchService and item model changes affect most lanes. Stabilize item schema first.

## Open Engineering Decisions

1. PWA vs native: recommendation is PWA for MVP.
2. Local-only vs hosted backend: recommendation is local-first PWA plus hosted AI proxy.
3. Embeddings vs keyword search: recommendation is keyword/attribute first, embeddings
   only after fixture data proves need.
4. Original photo retention: recommendation is keep local originals for MVP, add cleanup
   later.
5. Auth: recommendation is no auth for personal MVP.
